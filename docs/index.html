RiderHub

A riding club's garage, route planner and safety net — in one app that keeps working when the signal stops.

Built for Wander Pega. Plan a route with typed stops, ride it with turn-by-turn navigation, see where everyone else is, and keep a service history the workshop can actually read back. Runs entirely on free tiers.

01

The garage

Everything the bike needs, entered once.

Maintenance clocks that reset themselves

Every component — chain, oil, brake pads, coolant — carries its own interval in kilometres or months. Logging a service that replaced a part resets that clock automatically, so the same fact is never entered twice.

Service history the workshop can read back

Itemised parts with brand, quantity and warranty, alongside labour and tax. Records are editable after the fact — an invoice gets transcribed wrong, and deleting to re-enter would lose the service number and the maintenance reset that came with it.

Maintenance notes, closed by the service that fixed them

A rattle noticed mid-ride is written down with the odometer reading and how urgent it feels. Weeks later at the counter the list is still there — and when the service is logged, each note is ticked off against it. The history then records what was wrong, not only what was replaced.

Fuel, documents, reminders

Fill-ups give a running km/L. Insurance, PUC and registration are tracked by expiry date. Reminders fire on distance or date, and can reach the rider on Telegram.

02

The ride

Planned at the kitchen table, followed on the handlebars.

Stops that mean something

Each stop is typed — fuel, breakfast, lunch, night halt, sightseeing — numbered in order, and draggable to reorder. Night stops can pull up hotels nearby; fuel stops, the pumps actually on the route.

Bike routing, not a relabelled car route

The Bike profile sends TWO_WHEELER to the Routes API, which returns genuinely different roads. Alternatives come back sorted fastest-first, with the trade-off in distance shown next to each.

Navigation built for a helmet's eye line

The rider's marker sits low on the screen so the road ahead fills it, the map rotates to heading rather than north, and the compass blends GPS course with device orientation — course above walking pace, the magnetometer below it. A faster route found mid-ride is offered, not taken silently.

Fuel, food and a bed, from wherever you ask

Search near your current position, near any stop on the plan, or along the whole road ahead. Results carry rating, reviews and photos — proxied through the app's own server so the Maps key never reaches a browser.

03

Riding together

A club ride, not a fleet tracker.

Join by code, on your own terms

A group ride has a short invite code, shared through the phone's own share sheet. Whoever joins picks their own bike and their own starting point toward the shared destination — riders rarely leave from the same place.

Everyone else, at a glance

Other riders appear as lettered coloured discs with a last-seen time, so a marker that has gone stale is obvious rather than quietly wrong. Your own navigator stays exactly as it is when riding alone.

Polled, not pushed

Positions are fetched on an interval instead of held on a socket. For a club-sized group that is less machinery, it survives a patchy signal without a reconnect storm, and it is what let the whole API move to a serverless function without redesign.

04

When it goes wrong

And what a web app honestly cannot do.

One tap to raise it, four seconds to call

SOS sends the rider's position, blood group and medical notes to their contacts. A deliberate hold — not a tap — places the phone call, because a pocket press should not dial anyone.

Two contacts, each with their own thread

Each emergency contact gets their own WhatsApp conversation rather than a group, so nobody has to work out who is responding.

The limit, stated in the app

A browser cannot send a WhatsApp message or an SMS without the user tapping send — no web app can, whatever it claims. Telegram is the one channel that goes automatically, so that is what the app says: what was sent, and what is waiting on a tap.

05

Off the grid

Ghats and desert highways have no bars.

Ride packs

Route geometry, every turn instruction, the stops and the petrol pumps along the way are stored in IndexedDB before departure. The pack is deleted when the ride completes — but GPS fixes recorded offline and not yet uploaded survive that deletion.

No cached map tiles, on purpose

Google's terms forbid storing their tiles, so the offline view draws the route, the turns and the stops on its own canvas instead of pretending to be a map. Less pretty, and the only version that can actually ship.

Installs like an app

Home-screen icon, its own splash, and the shell cached so it opens instantly and works offline. Screen wake-lock keeps the display on while navigating; the layout handles landscape and a rotate control for bar-mounted phones.

06

Decisions worth defending

The ones that cost something to get right.

The database refuses every client

Firestore rules are deny-all. Nothing reads or writes directly — every path goes through the API, which uses the Admin SDK and checks ownership in code.

The rules this replaced let any signed-in rider read every profile in the club. Profiles hold phone numbers, blood groups and medical notes. One line of client SDK was all it took.

The Maps key is never in the bundle

It is fetched at runtime by signed-in riders only, and place photos are proxied through the server so the key stays there. A release guard reads the built bundle and fails the deploy if any server secret appears in it — including the ones nobody meant to add.

Money is never sent as a total

The client sends labour and each part separately; the server adds them up. The itemised figures and the total therefore cannot drift apart, however a record is later edited.

Two hosts, one source of truth

The same app deploys to Firebase Hosting with the API as a Cloud Function, or to an Always Free VM with Caddy terminating TLS and proxying to the API on a private port. A test reads the Caddyfile back against firebase.json so the two can never drift on caching or security headers.

They resolve overlapping header rules in opposite directions — Firebase takes the last match, Caddy the first. Written the way one host wants, every hashed asset came back no-cache on the other. The rules are mutually exclusive now, so neither ordering matters.
